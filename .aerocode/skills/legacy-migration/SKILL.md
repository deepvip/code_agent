# 老系统迁移手册

## 前置检查

1. 确认当前分支干净，或已创建 worktree（不要让迁移污染主工作区）。
2. 确认有可运行的测试基线；没有就先补 3～5 个冒烟用例。
3. 确认回滚方式：记录当前 commit，明确如何 revert。

## 执行节奏

**一次只迁移一个模块，跑通再下一个。**

```
读模块 → 列出受影响调用点 → 改实现 → 改调用方 → 跑测试 → 记录
```

- 每步改动控制在可 review 的规模（建议 < 400 行）。
- 发现「顺手能改」的无关问题时，记录下来但不要现在改。
- 遇到无法自动判定的语义差异，停下来问，不要猜。

## 常见坑

| 场景 | 检查点 |
|---|---|
| 依赖升级 | 传递依赖冲突、SPI 文件、序列化兼容 |
| API 替换 | 空值语义、异常类型、默认值变化 |
| 配置迁移 | 默认值是否变化、是否还有旧 key 在用 |
| 数据迁移 | 幂等、可重跑、失败可断点续传 |

## 收尾

输出一份迁移报告：

```
## 模块：xxx
- 改动文件：N
- 替换 API：A → B（M 处）
- 测试结果：通过/失败（失败原因）
- 待人工确认：...
- 遗留问题：...
```

## 禁止

- 禁止 `git push`、发布、部署。
- 禁止为了让测试通过而删除断言或跳过用例。
- 禁止一次性改完所有模块再统一跑测试。
